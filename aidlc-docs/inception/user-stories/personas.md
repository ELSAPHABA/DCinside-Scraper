# 페르소나

## 작성 기준

- 출처: `aidlc-docs/inception/requirements/requirements.md`
- 범위: 디시인사이드 공개 게시글 스크래퍼의 1차 구현
- 구성: CLI 사용자, 라이브러리 개발자, 워커 운영자, MCP 클라이언트, 유지보수자, 데이터 검토자

## P-001. 터미널 수집 사용자

**설명**: 로컬 PC나 서버 터미널에서 검색어, 게시글 URL, 수집 범위, 저장 옵션을 입력해 데이터를 수집하는 사용자입니다.

**목표**

- 게시글 URL, 갤러리 내 검색, 통합 검색 중 필요한 진입점으로 Job을 실행합니다.
- 이미지와 디시콘을 URL만 저장할지, 파일로 다운로드할지 선택합니다.
- CAPTCHA나 차단이 발생하면 중단점을 저장하고 나중에 재개합니다.

**불편한 점**

- 디시인사이드 검색 URL과 `search_pos` 규칙을 직접 다루기 어렵습니다.
- 중간에 차단되거나 네트워크 오류가 나면 어디까지 수집됐는지 추적하기 어렵습니다.
- Proxy와 User-Agent 설정 파일이 잘못되면 원인을 파악하기 어렵습니다.

**관련 스토리**: US-001, US-002, US-003, US-004, US-005, US-006, US-012, US-014, US-015

## P-002. Python 라이브러리 개발자

**설명**: 스크래퍼를 다른 Python 코드에서 import해 검색, 게시글 fetch, 댓글 fetch를 직접 호출하려는 개발자입니다.

**목표**

- CLI 실행 없이 core API로 수집 기능을 호출합니다.
- 결과 dataclass 또는 dict를 안정적인 JSON 구조로 직렬화합니다.
- import 시 네트워크 요청이나 파일 생성 같은 부작용이 발생하지 않게 합니다.

**불편한 점**

- CLI 전용 코드에 로직이 묶이면 재사용과 테스트가 어렵습니다.
- 반환 스키마가 불안정하면 downstream 분석 코드가 쉽게 깨집니다.

**관련 스토리**: US-007, US-008, US-009, US-010, US-011, US-012, US-016

## P-003. 워커 컨테이너 운영자

**설명**: 향후 통합 커뮤니티 스크래핑 시스템에서 디시인사이드 전용 워커 컨테이너를 실행하고 관찰하는 운영자입니다.

**목표**

- 컨테이너가 단일 Job을 안정적으로 수행하고 결과와 실패 기록을 남깁니다.
- structured logging으로 Job ID, stage, worker 상태를 확인합니다.
- 이전 이미지 또는 tag로 rollback할 수 있는 단순한 배포 구조를 유지합니다.

**불편한 점**

- 로컬 전용 상태 파일이나 상대 경로가 컨테이너에서 깨질 수 있습니다.
- 로그에 Proxy 비밀번호나 credential이 남으면 운영 위험이 커집니다.

**관련 스토리**: US-003, US-006, US-013, US-014, US-015, US-017

## P-004. MCP 클라이언트 사용자

**설명**: AI agent나 외부 도구에서 MCP tool 호출로 디시인사이드 수집 기능을 사용하려는 사용자입니다.

**목표**

- 게시글 fetch, 갤러리 검색, 통합 검색을 MCP tool로 호출합니다.
- CLI와 같은 core library 동작을 일관된 입력/출력 스키마로 사용합니다.
- 잘못된 입력은 명확한 validation 오류로 받습니다.

**불편한 점**

- MCP 계층이 별도 로직을 가지면 CLI와 결과가 달라질 수 있습니다.
- 오류 메시지가 내부 구현이나 secret을 노출하면 안 됩니다.

**관련 스토리**: US-012, US-014, US-016, US-018

## P-005. 유지보수자

**설명**: 디시인사이드 HTML 구조 변화, 댓글 API 변화, `(펌)` 구조 변화에 맞춰 파서와 테스트를 유지하는 개발자입니다.

**목표**

- HTML fixture와 PBT로 파서 회귀를 빠르게 발견합니다.
- CLI, 라이브러리, 컨테이너, MCP가 같은 core 함수를 공유하게 유지합니다.
- 차단 위험이 있는 live smoke test는 선택적으로 실행합니다.

**불편한 점**

- 파싱 규칙이 문서와 테스트에 남지 않으면 구조 변경 때 원인을 찾기 어렵습니다.
- Playwright 의존 로직이 들어오면 실행 환경과 테스트 비용이 커집니다.

**관련 스토리**: US-004, US-005, US-007, US-008, US-009, US-010, US-011, US-012, US-016, US-017, US-018

## P-006. 데이터 검토자

**설명**: Job별 JSONL 결과를 Polars DataFrame으로 불러와 누락, 중복, 스키마 안정성, 분석 가능성을 검증하는 사용자입니다.

**목표**

- Job 하나의 결과가 JSONL 파일 하나에 게시글 단위로 append되어 저장됩니다.
- `(펌)` 게시글도 일반 게시글과 같은 top-level 필드를 유지합니다.
- 댓글, 덧글, 이미지, 디시콘, 실패 기록을 분석 가능한 구조로 확인합니다.

**불편한 점**

- Job 간 결과가 한 파일에 섞이면 수집 조건별 검증이 어렵습니다.
- 제목 정규화나 repost 구조가 불안정하면 분석 코드에서 예외가 늘어납니다.

**관련 스토리**: US-006, US-009, US-010, US-011, US-012, US-013
